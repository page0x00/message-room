# 关系空间更新 · 2026-10-01

本轮从 main 的 `76083a4` 开始，在 `update/relationship-space-20261001` 分阶段开发、测试和推送，不合并 main，不清空线上数据。

## 阶段 1：账号身份

- 消息归属只比较 `author_id` 与 Supabase 当前用户 UUID。旧的 sender/device_id/昵称/头像都不参与归属判断。
- 现有访客可绑定邮箱，保留 UUID；新设备登录同一个邮箱。支持邮件链接/验证码、密码登录和验证后设置密码。
- 不再静默生成新访客。未登录时先展示账号页；用户可明确选择创建访客 UUID。
- 已加入的邀请房间从 room_members 找回。草稿、资料缓存、最近房间和通知游标按 UUID 隔离。
- 旧消息原样保留；缺失 author_id 的历史显示在左侧、使用历史称呼，不擅自认领。已有可靠 author_id 的记录保持原身份。

## Supabase 增量配置

1. SQL Editor 执行本分支 `supabase/INSTALL.sql`（可重跑，不删除旧消息）；已安装旧版也可只按日期执行新增 migration。
2. Authentication 开启 Email；需要继续使用访客时保留 Anonymous Sign-Ins，开启 Manual Linking，以便旧访客绑定邮箱。
3. URL Configuration 添加实际站点/测试预览 URL 到 Redirect URLs；Site URL 指向站点。邮箱模板可使用链接；如使用输入验证码，同时在模板展示 `{{ .Token }}`。
4. 在**原有访客所在设备**点击“账号与跨设备登录 → 绑定邮箱”，邮件确认后再在新设备登录同一邮箱。已属于其他邮箱账号的历史不会自动合并。
5. 历史无 author_id 的记录无法从昵称或设备安全证明归属。管理员若掌握可靠的原始归属证据，可在备份后按**明确消息 ID 列表**更新空 author_id；不得批量按昵称猜测。SQL 示例仅说明操作，替换核实后的 UUID 与 ID 才可执行：

```sql
begin;
-- 先 SELECT 核对，再对精确 ID 集合操作；不改 created_at、正文、附件。
select id, room_id, sender, author_id, created_at from public.messages
where id::text in ('核实后的消息ID');
update public.messages set author_id = '核实后的账号UUID'::uuid
where author_id is null and id::text in ('核实后的消息ID');
commit;
```

前端从未持有 service_role、邮箱密码或 VAPID 私钥；密码只传给 Supabase Auth，不落入应用缓存。
